# 하루 코스 저장과 복구 계약

하루 코스 저장 명령은 추천 패널 수명과 별개다. 사용자 ID·여행 ID·날짜로 격리하며, 시작 시 생성한 command ID로 이전 요청의 늦은 응답을 구별한다. 요청 경로·예상 revision·장소 순서·이동수단은 시작 당시 값으로 전송한다.

## 상태와 화면

- 저장 중: 같은 날짜의 새 코스 조회·추가 확정을 차단한다.
- 성공 또는 명시적 4xx 거절: 해당 명령만 종료한다. 성공은 원래 사용자·여행의 완료 버전을 올리고, 현재 그 여행을 표시하는 부모가 snapshot을 갱신한다. 날짜 전환·패널 제거 때문에 성공 갱신이 누락되지 않는다. 4xx는 완료 알림을 발행하지 않는다. 409이면 미리보기를 비우고 최신 일정 재조회를 안내한다.
- 통신 실패·5xx: 결과 불명확 상태로 전환한다. 자동 PATCH 재전송은 없다.
- 현재 일정 확인: 결과 불명확 명령만 조회 중으로 전환한다. 실패하면 결과 불명확 상태를 유지한다.
- 확인 성공: 원래 여행의 snapshot인지 확인하고 해당 응답을 부모 화면에 직접 전달한다. 같은 데이터를 다시 받기 위한 두 번째 GET은 하지 않는다.

패널 숨기기·이동수단 변경·날짜 전환·라우트 이탈로 컴포넌트가 제거되어도 원래 명령의 상태를 유지한다. 늦은 실패는 원래 날짜에만 기록하며 현재 표시하는 다른 날짜의 미리보기를 지우지 않는다. 결과 불명확한 날짜가 있어도 다른 날짜 작업을 일괄 차단하지 않는다.

같은 브라우저 탭의 sessionStorage에는 여행 ID·날짜·command ID만 저장한다. 새로고침 때 남은 명령은 결과 불명확으로 복원한다. 사용자별 키를 사용하며 다른 사용자에게 복구 상태를 적용하지 않는다. 토큰·장소 배열·메모·비용은 저장하지 않는다. 저장소 접근이 거절되면 살아 있는 탭 안의 메모리 상태를 유지한다. 그 경우 새로고침 이후 복원은 보장할 수 없다. 자동 TTL 만료로 확인 필요 상태를 임의 해제하지 않는다.

현재 일정 GET은 조회 시점의 상태 확인이며 과거 명령의 정확한 처리 이력을 증명하지 않는다. 새로고침·라우트 이탈은 서버 트랜잭션 취소가 아니다. 다중 탭 조정이나 서버 idempotency는 별도 계약이다. 서버의 revision·장소 순서·이동수단 검사와 쓰기 잠금이 계속 적용된다.

## 검증

상태 저장소 검사는 사용자/여행/날짜 격리, 이전 명령의 늦은 완료, reload 복원, 잘못된 저장 데이터, 저장소 거절을 확인한다. 브라우저 회귀 검사는 desktop/mobile의 409, 전송 전 실패, 실제 COMMIT 후 응답 유실, 숨기기/다시 켜기, 새로고침, 이동수단 변경, 날짜 변경과 늦은 실패·성공을 검사한다. 복구 전에 추가 PATCH가 없고 현재 일정·revision이 기대값대로 유지되는지 함께 확인한다.

여행 설정 변경·비용 설정 변경·삭제의 부모 잠금 대기 초과는 409/TRIP_WRITE_BUSY다. 이 세 작업의 OpenAPI는 필수 error/code/requestId를 가진 TripWriteConflict를 선언하며, 실제 DB 잠금과 HTTP 응답을 명세와 대조하는 검사를 유지한다.
