## 취소되는 SQL의 안전 경계

`readQuery`는 짧은 READ ONLY 트랜잭션과 문장당 3초 상한을 사용한다. 연결을 빌린 뒤 BEGIN·설정·조회·COMMIT·오류 rollback의 응답 확인 전체에도 3.5초 예산을 적용한다. 서버의 SQL 상한만으로는 응답이 유실된 연결을 반환할 수 없기 때문이다. 부모가 취소되면 별도 연결에서 `pg_cancel_backend`를 호출한다. 이 transport는 앱의 10개 풀 슬롯과 별도로 최대 2개 실행/32개 대기이며, 대기부터 종료까지 전체 1초·연결/문장/클라이언트 대기 각 500ms를 둔다. 취소 전용 연결은 공개 stream factory로 소켓을 소유하고 전체 기한에 소켓을 닫아 종료 응답 유실도 제한한다. source 값·SQL·좌표·인증 정보는 오류 로그에 기록하지 않는다.

취소 전송 성공을 실제 쿼리 종료로 간주하지 않는다. 취소 transport가 끝나거나 기한에 종료된 뒤 대상 연결을 풀에서 물리적으로 폐기한다. 응답을 기다리는 취소된 query 뒤에 ROLLBACK을 더 넣지 않으며, 연결 종료로 트랜잭션을 롤백한다. 취소되지 않은 일반 오류만 예산 안에서 명시적 rollback을 시도한다. 풀 획득이 늦게 완료되는 요청도 SQL을 실행하지 않고 연결을 반환한다. 취소 전달 실패 시 고정 이벤트를 기록하며, SQL 3초와 응답 확인 3.5초 상한 및 연결 폐기로 정리한다. 응답 종료와 내부 DB 정리 완료는 같은 시각이 아니다. 세 추천 API는 각 비동기 읽기를 부모 `budget.run`으로 감싸므로 SQL 취소·연결 정리가 늦어져도 HTTP 응답 기한을 늘리지 않는다. 핸들러의 예산은 기존 인증·접근·호출 제한 미들웨어가 통과한 뒤 시작한다. 쓰기 확정의 COMMIT에는 HTTP 취소를 적용하지 않는다.

PostgreSQL의 [취소 권한·동작](https://www.postgresql.org/docs/17/functions-admin.html)과 [pool 연결 반환 계약](https://node-postgres.com/apis/pool)을 기준으로 구현했다. API 역할과 취소 연결은 같은 DB 설정을 사용하며, 별도 특권이나 외부 취소 도구를 요구하지 않는다. 배포 환경에서도 해당 역할·연결·timeout 설정을 확인해야 한다.

## 검증과 원본 보존

새 회귀 24개를 운영 수정 전에 실행했을 때 19개 실패/5개 통과했다. 추가로 `4326d10`에서 SQL 정리를 지연시키는 모의 읽기 경계로 세 API의 HTTP 기한 반례를 재현했다(수정 전 3개 실패, 보강 후 3개 통과). 이는 실제 DB 취소/실패 fallback 검사와 별도이며, 35ms로 줄인 테스트 예산이 운영의 15초 예산을 대신하지 않는다. 이는 별도 [기준 반례](probes/README.md)와 함께 보존한다. 실제 PostgreSQL의 TCP 응답을 로컬 프록시에서 보류한 두 경우도 `84f6bd1`에서 실패한 뒤 보강 후 통과했다. 최종 네 가지 응답 유실 검사는 조회·BEGIN·자체 기한·취소 SQL의 응답 유실을 다룬다. 이 검사는 mock이나 운영 부하 측정이 아니다. 이후 SQL/HTTP/동시성 경계까지 새 Vitest 57개와 브라우저 2개를 추가했다. 최종 검증은 전체 Vitest 429개(52파일), 일회용 DB CI 묶음 361개(46파일), Python 34개, 전체 브라우저 33개(실제 발행 자료 6개 포함), 관광 CI 브라우저 4개 통과다. 타입·lint·전체 서식·OpenAPI/DBML·빌드 및 기존 지역 조회 부하 gate도 통과했다. 최종 결과와 검증 범위는 [실행 증거](tourism-operational-verification-20261006.json)에 기록한다.

기존 날씨 양성 테스트의 1일 축약 응답을 요청 계약인 10일로 수정했고, 후보 없음 테스트의 모의 조회를 실제 새 readQuery 경계로 옮겼다. 검사 강도를 낮추거나 정상 데이터 보호 규칙을 완화하지 않았다. 신규 테스트는 `test:ci`에, 브라우저 취소·시간 비교는 기존 CI의 `test:e2e:tourism`에 포함한다.

일회용 PostgreSQL에서 CI 묶음을 실행하고 DB를 제거했다. 전체 로컬 Vitest와 브라우저 검사는 기존 catalog·발행 자료가 있는 DB에서 실행하되 생성한 계정/장소/자료를 정리하고, 시작·종료의 catalog 수와 관광 snapshot/record/withdrawal 수 및 출처 상태를 대조한다. `.env`와 실행 중 생성된 화면/로그는 커밋하지 않는다. 기준 리뷰·반례는 과거 커밋의 상태를 설명하며 현재 결함으로 읽으면 안 된다.

## 남은 운영 검증

- 15초·SQL 3초·응답 확인 3.5초·취소 transport 상한은 시작 설정이다. 다중 API 인스턴스, 실제 Valhalla/Google/Open-Meteo 용량과 장애율에 맞춘 수치는 아직 아니다.
- 최종 자료 재검사는 `evidenceValidatedAt`의 DB 문장 시점 기준이다. 그 뒤 철회되거나 이미 전송한 응답을 즉시 회수하는 프로토콜은 없다. 원문 수집 시각과 최종 권리 검사 시각은 다르다.
- TRANSIT 연속 일정은 체류시간·출발시각·도착 이후 다음 출발을 연결하는 별도 기능이다. 현재 화면은 구간 비교만 제공한다.
- 권한은 기존 requireAuth/requireTrip과 호출 제한에서 검사한다. 장시간 요청 중 동행 권한 철회를 모든 단계에서 즉시 반영하는 새 접근 프로토콜은 추가하지 않았다.
- 전체 로컬 검사 첫 실행에서 관리자 입력 검사의 401 한 건이 관찰됐다. 인증을 재시도하거나 기대값을 완화하지 않고 등록 응답·오류 코드·요청 ID·DB의 역할/상태/유효 세션 유무 진단을 보강했다. 쿠키·토큰·해시는 출력하지 않는다. 반복 검사의 최종 결과는 실행 증거에 기록하며 원인이 확인되기 전에는 해결됐다고 주장하지 않는다.
- 배포 부하, 복원 RPO/RTO, 실외 현장 영업·행사 최신성, LLM 품질·AWS 배포 완료를 로컬 회귀와 CI 성공으로 주장하지 않는다.
