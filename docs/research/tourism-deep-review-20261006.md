## 결론

인증·일정 버전 검사·출처 승인·원자적 발행·철회 상속·제한된 재검색 같은 기본 구조는 갖춰져 있다. 그러나 공통 규칙이 추천 경로별로 다르게 적용되고, 외부 응답과 시간·취소·철회 경계의 계약이 충분히 명시되지 않았다. 현 상태를 “운영 수준에서 빈틈없이 검증됐다”고 평가할 근거는 부족하다.

이번에 **수정할 결함 5개(R1–R5)**와 **별도 설계가 필요한 경계 3개(D1–D3)**를 재현했다. P0/P1로 판단한 문제는 없지만, 이는 전체 앱의 취약점 부재를 증명하지 않는다. 이전 리뷰의 “추가로 재현한 P1/P2 없음”은 당시 검사 범위의 결론이며 아래 반례를 포함하지 않았다. 이번에는 실제 구현을 변경하지 않고 리뷰·설계·재현 자료를 작성했다.

권장 방향은 서비스 분할이나 LLM 추가에 앞서 **추천 규칙 통합 → 외부 응답 검증 → 취소·마감시각 → 시점 일관성 → 배포 환경 검증**이다. 세부 설계는 [아키텍처·워크플로우 설계](tourism-architecture-workflows-20261006.md)를 따른다.

## 수정할 결함

### R1 · P2 · 일반 추천에 명시적으로 닫힌 장소가 포함됨

위치: [day-alternatives.ts](../../server/day-alternatives.ts), `buildDayPlans` 76–104행 및 `candidatesAround` 154행.

일반 추천은 접근 제한·disused·abandoned를 검사하지만 `openingHours === 'closed'`와 `tags.opening_hours === 'closed'`를 공통 후보 단계에서 제외하지 않는다. `NEARBY`는 그대로 사용하고, `AUTO`의 음식점 분기도 실내·실외 검사보다 먼저 통과한다. 관광 그래프의 `isUsable`에는 해당 검사가 있다. UI의 공개 자료 옵션이 기본 꺼짐이므로 일반 경로도 주요 사용자 경로다.

재현: 닫힌 장소 1개와 정상 장소 3개를 같은 `buildDayPlans`에 넣으면 `NEARBY`에 닫힌 장소가 포함된다. 같은 입력을 관광 그래프로 보내면 제외된다. 실제 시설이 폐업했다는 주장이 아니라, catalog의 명시적 closed 표시에 대한 알고리즘 반례다.

수정: `PlaceEligibility` 공통 정책을 일반/관광 추천과 추천 확정 검증에서 사용한다. 알려진 접근 금지·폐쇄와 “영업시간을 모름”은 구분한다. 현재 저장된 일정을 읽을 때 폐쇄 장소를 몰래 삭제해서는 안 된다. 유지 요청 장소가 부적격이면 원인과 사용자 선택을 반환해야 한다.

수락 검사: 두 closed 필드 × 두 추천 엔진 × AUTO/INDOOR/NEARBY, 가까운 닫힌 장소와 먼 정상 장소, 영업시간 null은 정상 후보로 남는 대조군. 조회 뒤 닫힘으로 변경된 후보의 확정도 검사한다.

### R2 · P2 · KNOWLEDGE 코스는 같은 시설을 중복 방문 후보로 선택함

위치: [tourism-graph.ts](../../server/ai/tourism-graph.ts), `rules` 138–147행, `validateTourismPlans`의 ID 중복 검사. 대조: [place-dedupe.ts](../../server/place-dedupe.ts).

일반 코스는 `dedupePlaces`를 거치지만 KNOWLEDGE는 원래 `s.candidates`를 직접 정렬한다. 검증은 서로 다른 ID를 허용하므로, OSM node/way처럼 이름·좌표가 같은 두 레코드가 남는다.

재현: 같은 이름·동일 좌표의 `osm-node`, `osm-way` 중 하나에 시설 근거를 연결했다. KNOWLEDGE는 `[osm-node, osm-way, a]`, NEARBY는 `[a, osm-node, b]`를 선택했다. 같은 시설 두 번을 한 코스에 담는 차이가 확인됐다.

수정: 순위 결정 전에 시설 단위의 후보군을 만든다. 단순히 `dedupePlaces`를 먼저 호출하면 근거가 연결된 대표 ID가 잘릴 수 있다. 대표 선택은 유지 장소 → 직접 연결된 근거 → 품질 → 안정된 ID 순으로 명시하고, 다른 ID의 근거를 증거 없이 대표에 옮기지 않는다. 기존 체인 다양성 규칙은 실제 동일 시설 판별과 별개로 취급한다.

수락 검사: 두 번째 중복 ID에만 근거가 있는 경우, 유지 장소의 중복이 후보로 나온 경우, 같은 체인의 서로 다른 지점, 같은 이름의 떨어진 장소. 자동 병합 오탐을 막는 대조군이 반드시 필요하다.

### R3 · P2 · 서로 이어지지 않는 대중교통 시각을 합산해 완전한 미리보기로 표시함

위치: [tourism-graph.ts](../../server/ai/tourism-graph.ts) 293–332행, [day-alternatives.ts](../../server/day-alternatives.ts)의 `previewPlan`, [DayAlternatives.vue](../../frontend/src/components/DayAlternatives.vue)의 `preview.complete` 표시.

각 구간을 동시에 조회하면서 모두 여행일 오전 9시 JST 출발로 지정한다. A→B가 30분이어도 B→C 역시 9시 출발이다. 조회 성공만으로 `complete: true`가 되고 시간이 합산된다. 일반 `/routes` 응답에는 각 구간 9시라는 안내가 있지만 추천 미리보기에는 그 가정이 명확히 표시되지 않는다.

재현: 3장소 TRANSIT의 두 호출 모두 `2026-10-10T00:00:00.000Z`를 받았다. 각각 1,800초를 반환한 통제된 provider로 결과는 `complete: true`, 합계 3,600초다. 실제 Google 노선의 지연이나 실제 여행시간 오차를 측정한 것은 아니다. 문제는 서로 연결되지 않는 조회의 합을 연속 일정처럼 보여 주는 계약이다.

수정: 당장은 “구간별 동일 시각 비교”로 명시하고 전체 일정 실현 가능성과 분리한다. 연속 일정 기능은 첫 출발, 장소 체류시간, 이전 구간의 도착시간을 입력으로 다음 출발을 순차 계산한다. 체류시간을 근거 없이 만들어 넣지 않는다. 중간 구간 실패 뒤의 시각은 unknown이며 연속 합계를 제공하지 않는다. 자동차의 정적 경로까지 불필요하게 직렬화할 필요는 없다.

대중교통 출발·도착 시각과 시간표 제약은 [Google Routes 공식 문서](https://developers.google.com/maps/documentation/routes/transit-route)를 확인했다. 노선 조회 성공과 하루 일정의 실행 가능성은 다른 조건이다.

### R4 · P2 · 클라이언트 연결 종료 후 처리 중 요청 지표가 남음

위치: [metrics.ts](../../server/observability/metrics.ts) 24–28행.

시작 시 `inFlight++`를 실행하고 응답의 `finish`에서만 감소시킨다. 응답 완료 전에 클라이언트가 연결을 끊으면 `close`만 발생할 수 있다.

재현: 실제 loopback HTTP 요청을 서버가 받은 뒤 클라이언트 연결을 종료했다. 실제 열린 요청은 0인데 `bookhaedo_http_requests_in_flight`는 1이었다. 부하 판단 지표가 취소 횟수만큼 누적될 수 있다. 이번 실험은 지표 오류를 증명하며 서버 메모리 누수를 증명하지 않는다.

수정: `finish`와 `close`를 한 번만 처리하는 종료 함수에 연결한다. 중단은 성공 응답으로 집계하지 않고 별도 outcome에 기록한다. 활성 작업 수와 열린 HTTP 요청 수를 구분하면 취소 뒤 살아 있는 작업도 측정할 수 있다.

수락 검사: 정상 finish 후 close, finish 없는 close, handler 오류, 스트리밍 중단, 여러 요청 중 일부만 취소. 감소가 누락되거나 두 번 일어나지 않아야 한다.

### R5 · P2 · 불가능한 날씨 값이 정상 예보로 반환되고 캐시됨

위치: [providers.ts](../../server/providers.ts) 164–184행, 204–213행.

현재는 날짜 배열과 최고/최저 기온의 유한성을 주로 검사한다. 최고<최저, 강수확률 범위, 강수·풍속의 음수나 문자열은 충분히 검증하지 않는다. `ProviderCache.reusable`은 캐시 가능 여부일 뿐 반환값의 유효성을 보장하는 검증기가 아니다.

재현: 10일 날짜 배열과 `high=5`, `low=30`, 강수확률 `999`, 풍속 `-10`인 합성 응답이 `available: true`로 반환됐다. 같은 요청 두 번의 transport 호출은 1회여서 해당 응답이 캐시된 것도 확인했다. Open-Meteo가 실제로 이런 데이터를 보냈다는 주장은 아니다.

수정: provider 어댑터에서 원본 응답을 먼저 파싱해 검증된 Weather 타입만 캐시에 넣는다. 핵심 값 오류는 unavailable, 선택 항목 누락은 null, 선택 항목의 명백한 잘못된 값은 null+진단 또는 전체 거절 중 계약을 정한다. `0`, `null`, unknown을 구분하고 잘못된 자료로 악천후 여부를 확정하지 않는다.

수락 검사: 범위/단위/타입/배열 길이/날짜 중복/최고최저 역전/선택 필드 누락, 정상 0%·0mm·0풍속, 오류 다음 정상 응답의 복구와 캐시 오염 방지.

## 설계 계약을 먼저 명확히 할 경계

### D1 · 높은 우선순위 · 요청 전체의 마감시각과 연결 종료 취소가 없음

[tourism-graph.ts](../../server/ai/tourism-graph.ts) `bounded`는 날씨·생성·각 경로에 적용되지만 `retrieve`는 직접 await하며 신호를 받지 않는다. 라우트→`proposeTourism`→graph 입력에도 부모 요청의 신호가 없다. UI는 generation으로 늦은 결과를 무시하지만 실제 fetch를 취소하지 않는다.

실험에서 provider 제한을 10ms로 설정해도 검색을 80ms 지연하면 전체 그래프는 약 84ms 후 완료했다. **이 옵션이 전체 요청 제한이라는 주장은 하지 않는다.** 실험은 provider별 제한과 전체 마감시각이 다른 개념임을 확인한 것이다. DB에는 연결 5초·statement 15초 제한이 이미 있어 “아무 제한도 없다”는 지적은 틀리다. 여러 쿼리·재검색의 합계, 클라이언트 취소, 전체 작업 예산이 관리되지 않는 것이 남은 과제다.

`server.requestTimeout=30000`은 클라이언트의 요청 수신 제한이며 handler의 전체 실행 마감이 아니다. [Node HTTP 공식 문서](https://nodejs.org/api/http.html#serverrequesttimeout).

수정 방향: 요청 문맥의 단일 deadline·AbortSignal, 각 단계의 남은 예산, DB 취소/statement deadline, queue 취소를 연결한다. Promise.race로 응답만 끝내고 백그라운드 쿼리가 계속 실행되는 것을 성공으로 취급하지 않는다.

### D2 · 높은 우선순위 · 조회 이후 철회의 적용 시점이 정의되지 않음

검색은 매 시도 현재 승인·활성·철회를 확인하지만 마지막 검색 이후 route preview 동안 철회되면 최종 응답을 다시 검사하지 않는다.

일회용 DB에 가상 시설 1건을 발행하고, graph의 route 의존성에서 실제 `withdrawTourismRecord`가 커밋되도록 했다. 진행 중이던 추천은 `READY`, 근거 1건을 반환했고 이어진 새 검색은 근거 0건이었다. **철회 저장이나 이후 검색이 고장 난 것이 아니다. 진행 중 요청에 대한 적용 시점의 빈틈이다.**

수정 방향: 발행 버전 일관성과 권리 철회를 분리한다. 최종 응답 직전 한 번의 조회에서 현재 허용 여부를 재검사하고, “검사 시점에 유효함”을 계약으로 정의한다. 네트워크 전달 직전까지 절대 철회 노출 0이라는 보장은 짧은 재조회 하나로 만들 수 없다. 이미 사용자에게 전달된 화면에는 별도 TTL/재조회 정책이 필요하다. DB 잠금을 외부 경로 요청 내내 유지하는 방식은 피한다.

### D3 · 중간 우선순위 · 일정 revision과 items가 다른 시점에 읽힐 수 있음

[day-alternatives.ts](../../server/day-alternatives.ts) 139–150행의 일반 읽기는 별도 쿼리 두 개다. 실제 DB에서 첫 SELECT 후 별도 트랜잭션이 항목과 revision을 변경하도록 순서를 통제하면, 결과는 `revision=0`에 새 items가 들어 있고 DB의 revision은 1이다.

현재 확정 PATCH는 행 잠금 뒤 revision을 다시 검사하므로 오래된 추천으로 덮어쓰는 것은 막는다. 따라서 데이터 유실 결함으로 과장하지 않는다. 불필요한 409와 재조회, 일관되지 않은 응답의 문제다.

수정 방향: 단일 SQL로 day와 순서 있는 items를 읽거나 짧은 읽기 전용 REPEATABLE READ를 사용한다. 외부 요청 전 트랜잭션을 끝낸다. 교통수단 변경은 day revision과 별개이므로 향후 추천 문맥 버전에는 교통수단/출발시각도 포함한다.

관심 주제는 미구현이라고 단정할 수 없다. 실제로 전문검색 순위에 쓰인다. 다만 현재 rules가 근거 연결 여부와 거리로만 다시 정렬하므로, 120건 제한에 걸리지 않고 근거 집합이 같다면 주제를 바꿔도 코스 구성이 바뀌지 않을 수 있다. 제품이 개인화 코스를 약속하려면 retrieval 점수를 후보까지 전달하고 별도 평가셋으로 효과를 검증해야 한다.

일반 목록의 직선 동선은 일정 중심→첫 장소까지 포함하지만 실제 미리보기는 장소 간 구간만 합산한다. 중심은 사용자의 실제 출발지가 아니다. 현재 표시도 직선/실제 구분은 하지만, 비교 기준을 같은 endpoint로 맞추거나 검색 기준 거리와 방문 동선을 분리하는 편이 명확하다.

기존 [보고서](tourism-objective-review-20261006.md)의 시설 연결 28/137(20.4%)은 이번 DB 감사 수치가 아니다. 제품 우선순위의 참고 근거이며 현재 수치로 다시 단정하지 않는다. 실제 자료 확대보다 규칙 통합과 연결 품질 측정을 먼저 진행하는 편이 좋다.

## 잘못 지적하지 않도록 확인한 항목

- LangGraph는 실제 `StateGraph`로 구현됐다. 기본 생성이 rules인 것이며 AWS/LLM 미연결과 구분한다.
- POST 추천 사용자별 30회 한도는 별도 정책으로 적용된다. 이전 GET limiter skip 문제는 현재 코드에 없다.
- 자체 호스팅 Valhalla의 프로세스 동시성 8·queue 128 상한은 존재한다. 다중 프로세스의 합계 상한과는 다르다.
- 빈 일정 응답도 전역 requestContext의 no-store가 적용된다. 라우트에 다시 set하지 않았다는 이유로 누락이라고 판단하면 안 된다.
- 6곳 중 유지 최대 5개는 UI와 API에 같이 적용돼 있다. UI/API 불일치라는 의심은 철회했다. 제품 의도는 별도로 문서화할 수 있다.
- 일정 교체는 남는 장소의 메모·비용·시간을 보존하고 day revision을 올린다. 새 장소 추가·제외에 따른 데이터 변화는 명시해야 한다.
- 자료 철회는 별도 stable ID 표식으로 새 발행에도 상속된다. D2는 저장된 철회가 해제되는 문제가 아니다.
- 의존성 감사는 실패를 성공으로 바꾸는 래퍼가 아니다. 이번 CI 묶음의 실제 CLI 통합 테스트도 통과했다.

## 실행 가능한 수정 순서

1. R1/R2: 공통 후보 정책과 시설 중복 판별, 근거 대표 선택. 일반/관광·유지·확정까지 한 세트로 검증.
2. R5/R4: provider 파싱 후 캐시, 종료 exactly-once 지표. 외부 장애를 정상으로 보이지 않게 한다.
3. D1: 브라우저→HTTP→graph→DB/provider/queue 취소와 전체 deadline. 완료·취소·실패를 구분한다.
4. R3/D3/D2: 시간 의미·문맥 일관성·최종 권리 재검사. 기존 화면과 API 계약을 함께 갱신한다.
5. 별도 배포 환경: 실제 추천·경로 부하/다중 인스턴스/복원 훈련. 목표값 충족 전 운영 검증 완료로 표기하지 않는다.

각 단계는 원본 failing regression → 수정 → 대조군 → 관련 CI → 원격 SHA/CI 확인으로 완료한다. 실패하는 새 assertion을 삭제하거나 429/timeout/자료 없음 분기를 성공으로 간주해 숫자를 맞추면 안 된다.
