# 추천·경로 부하 측정 (2026-10-01)

실제 Express 인증·권한·DB·LangGraph·자체 호스팅 Valhalla를 호출했다. 합성 사용자 burst이며 운영 SLA·지속 처리량 측정이 아니다. 같은 후라노 4개 장소, WALK, 예보 범위 밖 날짜를 썼다. 날씨 API는 호출하지 않았다. 2 CPU·4GiB·2 처리 스레드, Valhalla 3.8.3, 로컬 홋카이도 OSM 파일(2026-09-07 이름)로 타일을 만들었다. 타일/Valhalla 내부 캐시는 초기화하지 않았다.

## 4개 장소 미리보기: cold, 3회 반복

## 결정 및 한계

- 사용자별 분당 30회 유지. 40회 실제 POST에서 1–30은 200, 31–40은 429를 모든 설정에서 확인했다. 실사용량에 근거한 최적 quota는 아니다.
- 프로세스당 경로 동시 호출 8개, 대기 128개를 기본으로 적용. 큐 대기까지 10초 상한에 포함하고, 넘침·취소는 직선거리/시간 미제공으로 처리한다. 응답 본문을 끝까지 읽은 후 슬롯을 반환한다. 공용 demo의 1.1초 규칙은 유지한다.
- 여러 API 프로세스/인스턴스면 상한이 합산된다. 운영 Valhalla 2스레드에서도 같은 결과를 보장하지 않는다. 긴 구간·다른 지역·TRANSIT/Google·날씨·네트워크·지속 도착률은 이번 비교 범위 밖이다.
- 4/8/16 순서 실행의 열·캐시 영향과 반복 3회의 한계가 있다. 개선 전 결과와 동일 harness·환경에서 비교했으나 무작위 교차 실험은 아니다.

## 재실행

loopback 자체 호스팅 Valhalla와 해당 4개 catalog 장소가 있는 DB가 필요하다. 테스트 계정만 생성·정리하며 catalog·기존 일정·snapshot은 변경하지 않는다. 서버 상한 변경은 프로세스 재시작이 필요하다.

```bash
VALHALLA_BASE_URL=http://127.0.0.1:8002 VALHALLA_MAX_CONCURRENT=8 npm run tourism:benchmark-recommendations -- --users 1,5,10,25 --rounds 3 --count 4 --output /tmp/tourism-load.json
```

이미지 실행 옵션의 근거: [Valhalla 3.8.3 공식 Docker 문서](https://raw.githubusercontent.com/valhalla/valhalla/3.8.3/docker/README.md). 기본 compose와 달리 이번 타일 생성은 transit/time-zone/elevation과 기본 속도 파일 다운로드를 사용하지 않았다. 운영 구성과의 차이를 포함한 로컬 검증이다.

## 6개 장소 추가 burst

동시 25·50명, 각 3회, 상한 8개로 실행했다. cold 미리보기 p95 중앙값은 각각 81.1ms, 107.7ms였다. HTTP 오류·불완전 미리보기·경로 실패는 0, 최대 동시 외부 호출은 8이었다. 동일 코스의 완료 캐시 재사용이 있어 모든 사용자별 경로가 전부 독립 cold 요청인 시험은 아니다. 큐 넘침 및 취소는 별도 회귀 테스트로 검증했다.

최종 코드에서는 환경 설정을 읽은 뒤 첫 경로 요청 때 gate를 한 번 초기화한다. 같은 1·5·10·25명 × 3회 harness를 다시 실행해 최대 동시 호출 8·HTTP 오류 0·불완전 미리보기 0을 확인했다. 이 실행은 JSON의 `finalRuntimeVerification`에 별도로 보존했으며 앞선 설정 비교값을 덮어쓰지 않았다.

상한 설정 비교는 행사·출처 확대 이전의 동일 코드·자료 상태에서 실시했다. 최종 gate 검증은 행사·출처 확대 이후이므로 그 응답시간을 앞선 비교값과 직접 비교하지 않는다.
