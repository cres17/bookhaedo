# 관광 파이프라인·CI 실패 경계 보강 — 2026-10-06

검증 기준은 `c217502`이다. 정상 fixture만 통과하는 검사에서 실제 URL·실제 npm 출력·입력 중 포커스 변경을 포함하는 검사로 확대했다. 이 문서는 실행한 범위와 남은 한계를 구분한다.

## 재현과 수정

| 입력·상황 | 수정 전 | 수정 후 |
| --- | --- | --- |
| 기록된 후라노 시설·행사 CSV의 퍼센트 인코딩 URL | Python 정제·TS 발행 거절 | 정제 → DB 발행 → 근거 검색에서 URL 그대로 유지 |
| 실제 npm 10.9.9의 HTTP 400 `Invalid package tree`·429·503·연결 거부 출력 | 모두 `fail`, 재시도 없음 | `retry`; 다음 유효한 보고서가 성공해야 통과 |
| npm 401·403·기타 400·잘못된 JSON | 실패 | 즉시 실패 유지 |
| 실제 npm high/critical 보고서 | 실패 | 첫 시도에서 실패, 재시도 없음 |
| 서버가 응답하지 않는 npm 요청 | 기존 계약에 검증 없음 | 자식 프로세스 제한 시간에 강제 종료, 최대 3회 후 실패 |
| 모달 내부에서 종료 시간 입력칸을 선택한 뒤 지연된 초기 포커스 실행 | 포커스가 시작 시간으로 이동 | 입력칸 포커스 유지, 저장 요청 `480–540` 검증 |

npm의 오류 출력은 `{error:{code:...}}`만으로 판단할 수 없다. npm 10.9.9 실행에서 확인한 최상위 `statusCode`, `body.message`, 네트워크 오류 `message`를 읽는다. 이 출력으로 원래 래퍼와 새 래퍼를 비교해 재시도 분류의 변경을 확인했다. HTTP 오류 payload에는 URL·헤더가 있으므로 실행 로그에 출력하지 않는다. 취약점과 오류가 함께 있는 혼합 보고서에서도 원문 전체 대신 심각도별 개수·패키지명·패치 여부만 기록한다. 이 혼합 경우의 기존 로그 노출을 회귀 테스트로 확인한 뒤 수정했다.

## 실패를 통과로 바꾸지 않는 조건

- high/critical은 합계 또는 취약점 목록 어디에 나타나도 즉시 실패한다. 종료 코드 0만으로 성공시키지 않는다.
- 성공에는 보고서 버전 2, 모든 심각도별 정수 개수, 합계 일치, 취약점 목록과 개수 일치가 필요하다. 예상하지 못한 구조·영구 오류·반복 장애는 실패한다.
- 허용한 재시도는 429·500/502/503/504, 지정한 네트워크 오류, 400 `Invalid package tree`뿐이다. 최대 3회, 대기 2초·4초, 프로세스는 회당 60초·출력 8MB로 제한한다. CI job도 15분으로 제한했다.
- 테스트의 내부 npm 네트워크 제한은 프로세스 제한보다 길게 설정하여, 래퍼 자체가 멈춘 프로세스를 종료하는지 따로 확인한다. 요청이 실제 loopback 서버에 도달했는지도 확인한다.
- URL은 입력 그대로 보존한다. 정상 UTF-8 일본어 파일명·인코딩된 공백은 허용하고, 점/슬래시/역슬래시/query/fragment 구조 인코딩, 이중 인코딩, 잘못된 UTF-8, 제어 문자, 다른 dataset·호스트·인증정보를 거절한다.
- 등록부 수정만으로 승인 범위가 넓어지지 않는다. 기존 출처 정책·라이선스·승인·활성 검사와 별칭 보호 조건은 유지한다.

## 테스트 자료의 성격

`tests/fixtures/npm-audit/npm-10.9.9.json`은 실제 npm CLI를 loopback 테스트 레지스트리에 연결해 얻은 출력이다. 테스트 서버의 포트와 HTTP 날짜만 정리했다. 장애 응답과 high/critical advisory는 통제된 가짜 데이터이며 실제 npm 서버에 장애를 일으킨 것이 아니다.

`tests/fixtures/tourism/resource-url-cases.json`은 저장된 실제 HARP 자원 URL 세 개와 우회/정상 인코딩 사례를 합친 31개 입력이다. Python과 TS가 각각 기대 결과를 만족하는지 검사한다. 승인·활성인 현재 출처 다섯 개의 실제 기록 또는 고정 URL도 모두 검사한다.

후라노 파이프라인 테스트는 실제 URL에 합성 CSV를 연결한다. SHA-256 blob과 SQLite 수집 보고서 → Python 정제 → TS 발행 → DB 검색까지 실행하고 URL·시설 연결을 확인한다. 새 HARP 파일을 실제 다운로드하거나 사용자용 snapshot을 새로 발행한 검증은 아니다.

전체 E2E 첫 실행에서 일정 수정의 종료 시간이 이전 값으로 전송되는 실패를 관찰했다. 변경 없는 반복 다섯 회에서는 재현되지 않았다. 별도로 초기 포커스 콜백을 지연시키는 결정적 검사를 추가했고, 수정 전 실패·수정 후 다섯 회 통과를 확인했다. 이 결과는 포커스 간섭을 재현한 근거이며 최초 입력 유실의 모든 원인을 확정한 주장은 아니다. 공통 dialog 수정과 이 화면 검사를 CI에도 포함했다.

추가 발행 자료 E2E의 최초 실행은 후라노·북토 네 개가 통과했고 삿포로 두 개는 가입 요청의 429로 실패했다. trace에서 `RateLimit-Policy: 50;w=900`을 확인했으며, 반복한 개발 서버들이 같은 DB 기반 인증 제한을 누적하고 있었다. Playwright API 서버에 `NODE_ENV=test`를 지정해 기존 프로세스별 namespace 격리를 사용하고, 실행 중인 개발 서버를 재사용하지 않도록 바꿨다. 한도·키·오류 응답은 그대로 적용한다. 테스트용 가입과 여행 생성 실패는 실제 상태 코드·본문을 검사하여 다음 실패를 진단할 수 있게 했다. 운영 서버의 제한이나 개발용 버킷을 지우지 않았다.

환경: macOS, Node 26.7.0, npm 11.19.0, 기존 PostgreSQL 17.5 + PostGIS 3.5.2. npm 10.9.9는 임시 폴더의 CLI로 추가 실행했으며 프로젝트의 npm·의존성 버전은 변경하지 않았다. 원격 CI는 Linux·Node 22를 사용하므로 그 결과를 별도로 확인한다.

catalog 20,810곳, 기존 관광 snapshot 7개·record 184개·withdrawal 0개와 활성 출처·라이선스 메타데이터를 검증 전후 대조했다. fixture 발행은 자신이 만든 자료를 정리하고 이전 활성 snapshot을 복원한다.

Windows의 CLI fallback, 실제 외부 장애 발생, 새 HARP 수집, 운영 동시 사용자·Valhalla 용량, AWS 배포는 이번에 검증하지 않았다. 지역 조회 부하 수치를 추천·경로 성능으로 해석하지 않는다. 인증 관련 과거 일회성 401의 원인을 해결했다고 주장하지 않는다.
