# AI 추천 POST 호출 제한 수정 — 2026-10-01

`POST /api/trips/:id/days/:date/ai-recommendations`가 GET 전용 `provider` 제한을 사용해 호출 집계를 건너뛰던 문제를 수정했다. 전용 `ai-recommendation` 정책은 인증 사용자당 60초에 30회를 허용한다. 같은 사용자의 로그인 세션·여행·날짜는 한도를 공유하고, 수락한 동행자는 별도 한도를 사용한다. 인증·여행 접근 검증 이후, 날짜 조회·추천·외부 provider 호출 이전에 집계한다. 빈 일정과 잘못된 입력도 이 한도에 포함한다.

초과 요청은 429 `AI_RECOMMENDATION_RATE_LIMITED`, `Retry-After`(초), draft-7 `RateLimit`·`RateLimit-Policy`, 요청 ID와 `Cache-Control: no-store`를 반환한다. 전역 API 제한이 먼저 적용되면 기존 `RATE_LIMITED`를 반환할 수 있다. 기존 GET 외부 조회 정책과 사용자 확정 PATCH는 별도이다. 생성 원본과 세 API 문서에 이 계약을 반영했다. DB 구조 변경은 없다.

## 수정 전후 재현

새 DB 회귀 테스트 3개는 기존 코드에서 모두 실패했다. 첫 30개 POST는 성공했고 31번째도 200이어서 429 기대가 실패했다. 수정 후 첫 30개가 200, 31~40번째 10개가 모두 429였다. 실제 Express 앱, 인증·동행자 권한 검사와 PostgreSQL 카운터를 사용했다. 정상 요청은 빈 일정으로 외부 호출을 피했고, 기존 날짜 조회 함수는 실제 구현을 호출하는 spy로 감시했다. 그래프는 호출 여부를 확인하는 mock이다. 제한된 요청이 날짜 조회나 그래프에 진입하지 않음을 확인했다.

별도 로그인 세션과 두 여행을 번갈아 사용해도 사용자 한도가 공유되고, 같은 여행의 수락 동행자는 첫 호출에서 남은 29회를 받는다. 추천 POST를 소진해도 GET 경로 조회는 자신의 별도 30회 한도에서 성공한다. 테스트 전용 PostgreSQL 버킷의 만료 시각을 과거로 변경해 60초 대기 없이 초기화 동작도 검증했다. 새 검사 파일은 `test:ci`에 포함했다.

## 실제 429 화면 검증

1440px·390px 화면에서 기존 코스와 미리보기는 fixture로 준비했다. 같은 사용자가 다른 빈 여행에 실제 추천 POST 30개를 보내 한도를 소진한 뒤, 현재 장소가 있는 여행의 미리보기 POST를 실제 API로 전달했다. 31번째 응답이 실제 429와 전용 오류 코드·Retry-After를 반환했다. 오류 안내와 기존 코스 목록이 남고, 미리보기·교체 버튼이 사라지며 저장된 일정이 유지됐다. 이후 fixture 미리보기를 복원해 기존 확정 PATCH가 실제 API/DB에서 성공하는 것도 확인했다. 제한 해제 후 실제 추천 품질이나 자동 재시도 기능을 평가한 결과는 아니다.
