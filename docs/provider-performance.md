# 외부 API 대기시간 개선

DB·로그인·화면 표시까지 포함한 후속 비교는 [로컬 배포용 빌드 브라우저 측정](browser-performance.md)을 참고한다. 이 문서의 외부 API 단축률과 브라우저 화면 단축률은 측정 범위가 다르다.

## 적용 범위

- 초기 진입: 세션, 지역 목록, 도시 파일을 동시에 요청한다. 일부 카탈로그 요청이 실패해도 성공한 데이터는 유지한다. 라우터의 인증 대기 조건은 유지한다.
- Valhalla 경로: 5분 동안 성공한 구간을 재사용한다. 키에 출발/도착 장소 ID·좌표·방향·이동수단·출발 시각·서버 주소·실행 환경을 포함한다. 일정에서 한 장소를 교체하면 캐시에 없는 인접 구간만 외부 요청한다.
- 경로 목록과 교통수단 비교, 하루 대안 미리보기: 최대 3개 작업을 병렬 처리하면서 원래 순서를 보존한다. 공용 Valhalla 요청 시작 간격 1.1초는 유지한다. 자체 호스팅/별도 주소에는 공용 서버용 전역 대기를 적용하지 않는다. 명시적으로 공용 주소를 설정해도 간격 정책은 유지한다.
- 날씨: 같은 좌표의 10일 예보를 10분 동안 공유한다. 조회하는 날짜마다 정확한 날짜의 값을 추출한다. JST 날짜가 바뀌면 새 예보를 요청하며, 현재 예보 범위를 벗어난 날짜는 캐시 조회 전 거절한다. 불완전한 예보는 저장하지 않는다.
- Google Routes: 같은 출발 시각·좌표·수단의 동시 요청만 합친다. 완료된 결과는 저장하지 않는다.
- Google Places: 이름과 거리 검증을 통과한 ID만 24시간 재사용한다. 리뷰·사진·상세 응답은 저장하지 않고 매번 조회한다. ID가 404를 반환하면 제거하여 다음 조회에서 재검색한다. 호출자의 취소 신호가 있는 ID 검색은 다른 호출과 합치지 않아 취소가 전파되지 않도록 한다.

Google Places 저장 범위 참고: [공식 Places 정책](https://developers.google.com/maps/documentation/places/web-service/policies). 장소 ID는 캐시 제한의 예외다.

캐시는 프로세스 메모리에 있고 제공자별 완료 데이터 및 진행 요청 추적을 각각 최대 512개로 제한한다. 재시작하면 비워진다. 여러 서버 인스턴스 사이에는 공유하지 않는다. 추적 한도에 도달한 새 키의 요청은 합치지 않고 실행한다. 이 캐시는 전역 동시성 제한기가 아니며 기존 API 요청 제한을 대체하지 않는다.

실패 응답과 직선거리 대체 결과는 저장하지 않는다. 만료된 데이터도 반환하지 않는다. 캐시 결과는 복제해 호출자 수정으로 다른 요청의 값이 바뀌지 않게 한다. 사용자별 여행 HTTP 응답은 캐시하지 않으며, 경로 조회 전 기존 소유자/멤버 권한 확인과 DB 조회를 유지한다. API 응답과 DB 스키마는 변경하지 않았다.

총 75회 fetch 요청 모두 HTTP 200이었고, 경로는 실제 Valhalla 이동시간·좌표, 날씨는 해당 날짜 예보, 장소는 검증된 Google 상세 응답임을 확인했다. 직선거리 대체 응답이나 조회 실패를 속도 개선으로 계산하지 않았다. 공식 웹사이트 유효성 검사에 사용하는 node:http 요청은 시간에는 포함되지만 fetch 호출 수에는 포함되지 않는다. Google 사진 다운로드는 제외했다.

**한계:** 버전당 3회인 소규모 측정이다. DNS/TLS, 제공자 측 캐시·부하 변동은 남아 있다. 앱 HTTP 처리·인증·DB·운영 인그레스·브라우저 렌더링과 동시 사용자 부하는 포함하지 않으므로 운영 p95나 화면 전체 단축률로 사용하면 안 된다. 측정 실패했던 샌드박스 네트워크 차단 실행은 이 표에서 제외했다.

- 원본 측정: [provider-live-measurement.json](benchmarks/provider-measurement-20260922.json) — 회차별 시간·단계별 시간·상태코드·기준 커밋·소스 해시만 기록했다. 제공자 본문과 비밀키는 저장하지 않았다.
- 재실행: `npm run benchmark:providers:live -- --live --baseline 71bca6f --rounds 3`
- 실제 Google 요청에는 과금이 발생할 수 있다. 스크립트는 1–5회차만 허용하며, DB나 사용자 여행 데이터는 변경하지 않는다.

배포 환경의 단축률을 완성하려면 개선 전후 서비스 주소 또는 비교 가능한 운영 지표 기간, 같은 권한·일정의 테스트 계정이 필요하다. 현재 배포 주소를 찾지 못했고 이 측정에서 운영 배포는 수행하지 않았다.

기존 `/internal/metrics`에 다음 지표를 추가했다. 프로덕션에서는 기존 Bearer 토큰 인증이 필요하다.

- `bookhaedo_provider_cache_total{provider,outcome}`: `hit`는 완료 결과 재사용, `joined`는 진행 중 요청 합류, `miss`는 로더 실행, `failed`는 로더 실패/저장 불가 결과, `bypass`는 진행 요청 추적 한도 초과다. `failed`, `bypass`는 `miss`의 부분집합이므로 모두 합산하지 않는다.
- `bookhaedo_provider_load_duration_seconds_total{provider}`: 로더 실행 시간 합계. `miss` 증가량으로 나누면 평균 로더 대기시간이다. Google 장소 ID 지표에는 별도 상세 요청이 포함되지 않는다.
- 기존 `bookhaedo_http_request_duration_seconds` 히스토그램: 동일 부하에서 경로/날씨 API의 p50·p95를 비교한다.

재사용률은 `(hit + joined) / (hit + joined + miss)`로 계산한다. 지표에는 좌표·사용자 ID·인증키·검색어를 기록하지 않는다. 초기 빈 캐시와 재사용 가능한 캐시를 구분해 비교하고, 날씨 10분·경로 5분의 갱신 주기를 고려한다. 실제 운영 p95와 외부 제공자 과금 감소율은 운영 데이터 수집 후 판단한다.
