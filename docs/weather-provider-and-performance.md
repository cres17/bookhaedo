# 날씨 제공자 교체와 외부 API 호출 최적화

정리일: 2026-09-28. 기존 코드·검증 기록과 2026-09-22 측정 결과를 정리했다. 문서 정리를 위해 외부 API 실험을 새로 실행하지 않았다.

**제공자 교체와 후속 성능 개선은 별개다.** Google Weather에서 Open-Meteo로 바꾼 이유는 당시 일본 일별 예보 요구사항을 충족하기 위해서다. 아래 단축률은 이미 Open-Meteo를 사용하던 기준 코드와 로컬 최적화 작업본을 비교한 결과다.

이 변경에는 성능 최적화 구현과 설계 설명·측정 데이터를 함께 포함한다. 아래 성능 수치는 2026-09-22 당시 작업본의 기록이며 최신 병합본을 다시 측정한 수치는 아니다. 기준 커밋은 [`71bca6f`](https://github.com/cres17/bookhaedo/tree/71bca6fd326d78c5fd4c3037fcd63fcb96a2c653)이며, 측정 당시 전후 제공자 파일의 SHA-256은 [원본 측정 데이터](benchmarks/provider-measurement-20260922.json)에 있다.

## 1. 왜 제공자를 바꿨는가

홋카이도 여행 플래너에는 장소 좌표와 여행 날짜에 맞는 **일별 예보**가 필요하다. 일정에 날씨를 표시하고 야외 활동이 어려운 조건에서 실내 대안을 찾는 입력으로 사용하기 때문이다.

[당시 검증 기록](test-report.md)에 따르면, Google Weather 활성화 이후에도 일본 좌표의 조회가 HTTP 404를 반환했다. 지도와 Routes는 정상화됐지만 날씨는 해결되지 않았고, 당시 공식 지원 범위를 확인해 일본 일별 예보 미지원으로 판단했다. 대상 지역·예보 단위가 서비스 요구사항과 맞지 않아 Open-Meteo로 교체했다.

이는 당시 연동 기록의 설명이다. 현재 Google Weather의 지원 범위를 새로 조사한 결과가 아니며, Google의 응답 속도나 예보 정확도가 낮았다는 주장이 아니다.

## 2. 교체와 날씨 기능 연결에서 구현한 것

[예보 조회 코드](../server/providers.ts)의 `forecast(latitude, longitude, date)`는 외부 데이터를 서비스가 사용하는 일별 날씨 형식으로 변환한다.

| 구현 | 구체적인 처리 |
| --- | --- |
| 좌표 기반 요청 | Open-Meteo `/v1/forecast`에 위도·경도와 일별 기상 항목 요청 |
| 일본 날짜 기준 | `Asia/Tokyo`의 오늘부터 9일 뒤까지 허용하고 `daily.time`에서 요청 날짜 검색 |
| 화면·추천용 응답 | 최고·최저 기온, 한국어 날씨 설명, 강수량·적설량·강수확률·풍속과 출처 반환 |
| 단위 통일 | 풍속 요청 단위를 km/h로 지정해 추천 임계값과 일치 |
| 실패 처리 | 범위 밖 날짜는 외부 호출 없이 안내. 9초 제한, HTTP 오류, 날짜·기온 누락 시 `available: false` 반환 |
| 기능 연결 | 일정 화면의 예보·출처 표시와 대상 장소 좌표의 실내 대안 판단에 연결 |

[공통 날씨 정책](../shared/weather-policy.ts)은 비·눈·이슬비·뇌우 또는 강수량 5mm, 적설량 1cm, 강수확률 70%, 풍속 40km/h 이상 중 하나이면 악천후 추천 조건으로 판단한다. 이는 서비스 추천 기준이며 공식 기상특보 기준은 아니다.

## 3. 어느 범위까지 확인했는가

- **실제 외부 연동:** 삿포로 좌표의 오늘·내일·모레 예보를 실제 API로 받아 날짜와 유효한 기온을 확인했다. 실제 예보가 일정 화면에 표시되는 흐름은 [브라우저 테스트](../tests/e2e/google-live.spec.ts)와 기존 검증 기록에 있다.
- **실제 악천후 사례:** 2026-09-09 기록에는 삿포로 이슬비·강수확률 100% 예보에서 실내 후보 3곳을 반환하고, 선택 후보의 기존·변경 인접 경로를 실제 Valhalla로 비교한 결과가 있다.
- **통제된 조건의 저장 검증:** 예보·추천 응답을 고정한 데스크톱·모바일 테스트에서 미리보기, 취소, 교체 확정, 새로고침 후 유지, 저장 충돌 시 기존 일정 보존을 확인했다. 계정·여행 생성과 최종 저장·재조회는 실제 DB를 사용했다.

상세한 구분은 [날씨 대안 검증 기록](weather-alternatives-evaluation.md)을 참고한다. 일본 전 지역·모든 날짜·모든 실제 악천후 조합을 전수 검증한 결과는 아니다.

## 4. 후속 최적화에서 바꾼 호출 구조

### 날짜마다 다시 받던 10일 예보 공유

기준 코드도 한 번의 요청으로 10일 예보를 받지만, `forecast()`를 호출할 때마다 외부 요청을 다시 수행했다. 같은 좌표의 오늘·내일·모레를 조회하면 같은 기간의 예보를 세 번 받았다.

로컬 개선본은 좌표·조회 항목·시간대와 일본 기준 오늘 날짜를 키로 삼아 10일 예보를 10분간 재사용한다. **조회할 여행 날짜는 캐시 키에서 제외하고, 공유된 응답에서 해당 날짜의 값을 추출**한다. 일본 날짜가 바뀌면 키가 바뀌고, 범위 밖 날짜는 캐시를 확인하기 전에 거절한다.

```text
개선 전: 오늘 조회 → 10일 예보 요청
         내일 조회 → 10일 예보 요청
         모레 조회 → 10일 예보 요청

개선 후: 오늘 조회 → 10일 예보 요청·저장 → 오늘 값 추출
         내일 조회 → 저장된 10일 예보에서 내일 값 추출
         모레 조회 → 저장된 10일 예보에서 모레 값 추출
```

### 변경 파일과 최적화 방식

아래 경로에 최적화 구현이 포함되어 있다. 측정 당시 소스 해시는 원본 JSON으로 구분한다.

| 파일 | 변경 내용 |
| --- | --- |
| `server/provider-cache.ts` | 유효기간·용량 제한이 있는 공통 캐시. 진행 중인 Promise를 공유해 같은 키의 동시 호출을 합치고, 완료·실패 후 진행 요청 제거 |
| `server/providers.ts` | 날씨 조회를 공통 캐시로 감싸고 10일 응답에서 날짜별 값 추출. Google Routes는 완료 결과 저장 없이 동시 중복 요청만 합침 |
| `server/routing.ts` | 성공한 Valhalla 구간을 5분 재사용. 출발·도착 ID와 좌표, 방향, 수단, 출발 시각, 서버·실행 환경을 키에 포함 |
| `server/routes/providers.ts`, `server/day-alternatives.ts` | 독립 구간을 최대 3개씩 처리하고 결과 순서 유지. 기존 Valhalla 요청 시작 간격 1.1초 유지 |
| `server/place-details.ts` | 이름·거리 검증을 통과한 장소 ID를 24시간 재사용. 상세·리뷰·사진 응답은 저장하지 않고 ID 조회 404 시 제거 |

캐시는 완료 데이터와 진행 요청 추적을 각각 최대 512개로 제한한다. 만료된 값을 반환하지 않고, 결과를 복제해 한 요청의 수정이 다른 요청에 영향을 주지 않도록 한다. 실패 결과나 직선거리 대체 경로는 재사용하지 않는다. 날씨는 10일 날짜의 연속성과 각 날짜의 최고·최저 기온을 검사해 불완전한 응답이 캐시에 남지 않게 한다.

예를 들어 A→B→C→D는 최초 세 구간을 조회하고 재조회 시 재사용한다. B를 X로 교체하면 A→X와 X→C만 새로 요청하고 C→D는 재사용해, 전체 시나리오의 외부 호출이 9회에서 5회로 줄어든다.

이 캐시는 프로세스 메모리에 있으며 서버 재시작 시 비워진다. 여러 서버 간 공유 캐시나 전역 동시성 제한기가 아니다. 사용자별 여행 HTTP 응답을 통째로 저장하지 않으며 여행 접근 권한 검사는 유지한다.

## 5. 실제 외부 API 비교 결과

2026-09-22에 기준 커밋과 개선본을 새 프로세스·빈 애플리케이션 캐시에서 시작해 각각 3회 측정했다. 동일 시나리오를 사용하고 회차마다 실행 순서를 바꿨다. 수치는 시나리오 전체 처리시간의 중앙값이다.

| 실제 API 시나리오 | 외부 호출/회차 | 개선 전 | 개선 후 | 단축률 |
| --- | ---: | ---: | ---: | ---: |
| 같은 좌표의 오늘·내일·모레 예보 | 3 → 1 | 1,603.60ms | 984.97ms | 38.58% |
| 4개 장소 경로 최초 조회 → 재조회 → 중간 장소 교체 | 9 → 5 | 9,057.70ms | 4,652.32ms | 48.64% |
| 같은 장소 상세 2회 조회 | 4 → 3 | 1,918.92ms | 1,642.55ms | 14.40% |

총 75회 fetch 요청 모두 HTTP 200이었다. 실패·직선거리 대체 결과는 성공 측정으로 계산하지 않았다. 공식 웹사이트 확인용 별도 HTTP 요청은 처리시간에 포함되지만 fetch 호출 수에는 포함되지 않으며, Google 사진 다운로드는 제외했다.

단축률은 `100 × (1 - 개선 후 중앙값 / 개선 전 중앙값)`이다. [원본 JSON](benchmarks/provider-measurement-20260922.json)에 회차별 값·호출 수·HTTP 상태·기준 커밋·소스 해시를 공개했다. 키·세션·제공자 응답 본문은 포함하지 않는다.

**해석의 경계:** 과거에 측정해 둔 교체 전 성능이 아니라, 기존 코드와 개선본을 같은 시점에 실행한 소규모 로컬 비교다. 실제 외부 API를 호출했지만 앱 HTTP·DB·로그인·화면 렌더링·운영 인그레스·동시 사용자 부하는 포함하지 않는다. 따라서 서비스 전체 응답시간, 운영 p95 또는 SLA로 해석하지 않는다. 첫 경로 조회는 거의 같았고 장소 상세는 한 회차에서 개선본이 더 느렸으므로 모든 요청의 일관된 가속을 주장하지 않는다.

특히 **날씨 38.58%는 Open-Meteo 중복 호출 최적화 효과**이며 Google Weather와 Open-Meteo의 속도 비교가 아니다. 경로의 재사용과 병렬 처리를 각각 분리한 실험도 아니므로 한 기법만의 효과로 해석하지 않는다.
